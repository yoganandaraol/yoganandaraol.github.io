01
AsNoTracking() — Read-Only Query Optimization Query Efficiency
Eliminates Change Tracker overhead for pure reads
Memory Pressure CPU — Change Detection Query Latency

Core Concept

By default EF Core registers every materialized entity in its Identity Map and Change Tracker. This allows SaveChanges() to detect mutations automatically via snapshot diffing. AsNoTracking() bypasses this pipeline entirely — entities are returned as plain POCOs with no internal proxy wrappers or snapshot allocations.

Problem If Ignored

  • Each tracked entity: ~2–4x memory overhead (original + snapshot)
  • DetectChanges() scans ALL tracked entities on SaveChanges
  • Under high concurrency this saturates LOH and triggers GC Gen2 pauses
  • DbContext lifetime leaks cause identity map bloat across requests

When To Use

  • GET endpoints, API projections, reports, dashboards
  • Any query where you do NOT call SaveChanges() on the result
  • Background jobs reading for processing (not writing back)

Production Impact If Skipped

  • Throughput degradation under load (GC pressure)
  • Increased p99 latency in high-read workloads
  • Memory leaks in scoped DbContext misuse patterns
❌ TRACKED — unnecessary overhead
// EF creates snapshots + tracks every Order entity
var orders = await _db.Orders
    .Where(o => o.CustomerId == customerId)
    .ToListAsync();
✅ AS NO TRACKING — zero change tracker cost
// For read-only API endpoints
var orders = await _db.Orders
    .AsNoTracking()
    .Where(o => o.CustomerId == customerId)
    .ToListAsync();

// Set globally for read-only DbContext variants
protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
{
    optionsBuilder.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
}
ARCHITECT NOTE › Register two DbContext variants in DI: a read-only one with NoTracking as default + a write-capable one. Route read endpoints to the read context. This eliminates entire classes of accidental mutation bugs in addition to the perf gains.
02
N+1 Problem — Include() vs DTO Projection Query Efficiency
The single most common EF Core performance killer in production
DB Round-Trips Network Saturation Query Explosion

Core Concept

N+1 occurs when you load a collection (1 query) and then access a navigation property per item (N queries). With lazy loading enabled, this is invisible in code but catastrophic at runtime. The fix is either eager loading via Include() (JOIN-based) or DTO projection via Select() (targeted SQL).

Problem If Ignored

  • 100 orders = 101 SQL queries instead of 1
  • DB connection pool exhaustion under moderate load
  • Timeouts cascade: each lazy load consumes a connection slot
  • Invisible in development (small dataset), catastrophic in prod

Include() vs Projection — When?

  • Include(): when you need full entity graph and will track/modify
  • Select() projection: always preferred for API reads — returns only needed columns, avoids cartesian explosion risk with multiple Includes

Deployment Impact

  • DB CPU spikes during traffic bursts
  • Read replicas overloaded with redundant queries
  • APM tools show hundreds of near-identical SQL statements
❌ N+1 DISASTER — lazy load in a loop
var orders = await _db.Orders.ToListAsync(); // Query 1
foreach (var order in orders)
{
    // Each access fires a SELECT — N more queries!
    var name = order.Customer.Name;
}
✅ EAGER LOAD with Include() — single JOIN query
var orders = await _db.Orders
    .Include(o => o.Customer)
    .Include(o => o.Items).ThenInclude(i => i.Product)
    .AsNoTracking()
    .ToListAsync();

// ─── PREFERRED for APIs: DTO Projection ───────────────
var dtos = await _db.Orders
    .AsNoTracking()
    .Select(o => new OrderSummaryDto
    {
        OrderId      = o.Id,
        CustomerName = o.Customer.Name,   // EF generates JOIN — no N+1
        TotalItems   = o.Items.Count(),
        TotalValue   = o.Items.Sum(i => i.Price)
    })
    .ToListAsync();
ARCHITECT NOTE › Multiple Include() on collection navigations generates cartesian products (SQL cross-join explosion). For complex graphs, use AsSplitQuery() to emit separate optimised SELECTs per navigation. Measure both — split queries add round-trips, cartesian multiplies rows.
03
Select() Column Projection Query Efficiency
Stop SELECT * — fetch only what your caller needs
I/O Bandwidth Network Transfer Heap Allocation

Core Concept

EF Core translates LINQ Select() projections into targeted SQL column lists. Without projection, EF emits SELECT * which pulls every column — including large BLOBs, XML fields, and audit columns — even when your caller only displays two fields.

Problem If Ignored

  • Serialising unused columns wastes DB → app → client bandwidth
  • Large NVARCHAR(MAX)/VARBINARY columns bloat the result set dramatically
  • Wider rows = fewer rows fit in buffer pool pages = more I/O
  • JSON serialiser (System.Text.Json) processes and allocates ALL properties

Always Project For

  • List/search endpoints (return DTOs, not entities)
  • Dropdown/autocomplete queries (id + name only)
  • Dashboard aggregations (compute server-side)

Deployment Impact

  • Reduced SQL Server buffer pool pressure
  • Lower ASP.NET serialisation CPU
  • Reduced response payload = lower CDN egress costs
❌ FULL ENTITY — pulls all 40 columns including Resume BLOB
var employees = await _db.Employees
    .Where(e => e.DepartmentId == deptId)
    .ToListAsync(); // SELECT * — includes Photo, Resume, etc.
✅ PROJECTED — targeted SQL, minimal allocation
// Dropdown: just id + name
var lookup = await _db.Employees
    .Where(e => e.DepartmentId == deptId && e.IsActive)
    .Select(e => new { e.Id, e.FullName })
    .AsNoTracking()
    .ToListAsync();

// Rich DTO — only the columns the card UI renders
var cards = await _db.Employees
    .AsNoTracking()
    .Select(e => new EmployeeCardDto
    {
        Id         = e.Id,
        FullName   = e.FullName,
        Title      = e.JobTitle,
        Department = e.Department.Name,
        // No Photo, Resume, AuditFields — saves 200KB per row
    })
    .ToListAsync();
ARCHITECT NOTE › Combine with AsNoTracking() — projected anonymous types and DTOs cannot be tracked anyway (no key identity), so EF skips tracking automatically. But explicit AsNoTracking() signals intent and avoids ambiguity.
04
Database Indexes on Filter & Join Fields Schema & Indexing
EF migrations give you index control — use it systematically
I/O — Table Scans Query Plan Lock Escalation

Core Concept

EF Core only creates indexes automatically for primary keys and foreign keys. Every WHERE, JOIN ON, and ORDER BY column in your hot queries needs an explicit index defined in OnModelCreating or via Data Annotations. Without indexes, SQL Server performs full table scans — O(n) per query regardless of data.

Problem If Ignored

  • Full scans lock pages longer → lock escalation → blocking chains
  • Query cost grows linearly with table size — silent until scale
  • Missing index on FK = slow joins and cascade operations
  • Composite indexes order matters: (A,B) ≠ (B,A) — wrong order = no index seek

Index Strategy Rules

  • Every FK column gets an index (EF doesn't auto-create)
  • Composite: put highest-selectivity column first
  • Covering index: include non-filter columns to avoid key lookups
  • Filtered index: partial index for IsDeleted = 0 patterns

Deployment Impact

  • Missing indexes on a 10M row table = seconds per query
  • Full scans cause autovacuum/maintenance storms on high write tables
  • Index rebuilds need maintenance windows on large tables
✅ SYSTEMATIC INDEX DEFINITION in Fluent API
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Order>(e =>
    {
        // Single column index on FK (EF doesn't auto-create!)
        e.HasIndex(o => o.CustomerId);

        // Composite: filter by status + date range (order matters!)
        e.HasIndex(o => new { o.Status, o.CreatedAt })
         .HasDatabaseName("IX_Orders_Status_CreatedAt");

        // Covering index: include columns to avoid key lookup
        e.HasIndex(o => o.CustomerId)
         .IncludeProperties(o => new { o.TotalAmount, o.Status });

        // Filtered index: only active orders (EF8+ / raw SQL fallback)
        e.HasIndex(o => o.AssignedUserId)
         .HasFilter("[IsDeleted] = 0");
    });
}
ARCHITECT NOTE › Run sys.dm_db_missing_index_details (SQL Server) or pg_stat_user_tables (Postgres) in staging with production-sized data. Let the query engine tell you what it needs — then translate those recommendations back into EF Fluent API index definitions. Never index-by-instinct on large tables.
05
ExecuteUpdate / ExecuteDelete — Direct DB Ops Bulk Writes
EF7+ bulk operators that bypass the entity pipeline entirely
No Entity Materialisation Single SQL Statement No Change Tracker

Core Concept

Before EF7, updating 10,000 rows required: load all 10,000 entities → mutate each → SaveChanges() detects changes → emits 10,000 UPDATE statements. ExecuteUpdateAsync() translates directly to a single UPDATE … WHERE statement — no materialisation, no change tracking, no round-trips per entity.

Problem If Ignored

  • Loading 50K entities to update one column: 50K object allocations + GC
  • 10K individual UPDATEs: transaction log explosion, lock escalation risk
  • Timeout failures on large batch operations
  • Locks held for duration of entire round-trip loop

When To Use

  • Bulk status updates (archive, soft-delete, flag)
  • Scheduled jobs processing large datasets
  • Admin operations: reset, recalculate, re-assign
  • NOT when: you need to fire domain events, run interceptors, or need optimistic concurrency per row

Deployment Impact

  • Job that took 45s → ~200ms (measured in real systems)
  • Transaction log size: N individual UPDATEs vs 1 batch UPDATE
  • Lock duration: seconds vs milliseconds
❌ ENTITY LOAD LOOP — catastrophic at scale
var expiredOrders = await _db.Orders
    .Where(o => o.ExpiresAt < DateTime.UtcNow)
    .ToListAsync(); // Loads 50,000 entities into memory

foreach (var o in expiredOrders)
    o.Status = OrderStatus.Expired;

await _db.SaveChangesAsync(); // 50,000 UPDATE statements
✅ ExecuteUpdateAsync — single SQL UPDATE WHERE
// EF7+ — generates: UPDATE Orders SET Status = 2 WHERE ExpiresAt < @now
var affected = await _db.Orders
    .Where(o => o.ExpiresAt < DateTime.UtcNow)
    .ExecuteUpdateAsync(s => s
        .SetProperty(o => o.Status, OrderStatus.Expired)
        .SetProperty(o => o.UpdatedAt, DateTime.UtcNow));

// Soft delete — single DELETE WHERE (EF7+)
await _db.AuditLogs
    .Where(l => l.CreatedAt < DateTime.UtcNow.AddYears(-7))
    .ExecuteDeleteAsync();
ARCHITECT NOTE › ExecuteUpdate/Delete bypass domain interceptors, audit triggers registered via EF SaveChanges, and optimistic concurrency tokens. Enforce a convention: bulk ops go through a dedicated BulkOperationsService that explicitly documents this bypass. This prevents hidden audit gaps in regulated systems.
06
Delay ToList() — Keep Work on the Server Query Efficiency
IQueryable composition vs IEnumerable — the pipeline boundary
Memory Allocation Data Transfer Client-side Processing

Core Concept

Calling ToList() / ToArray() materialises the IQueryable into memory, ending SQL composition. Any LINQ after that point runs in C# on the full dataset. Delaying materialisation keeps the WHERE, SELECT, GROUP BY, ORDER BY in SQL — executed by the database engine on indexed data.

Problem If Ignored

  • Entire table loaded into ASP.NET memory before filtering
  • C# LINQ has no indexes — sequential scan on in-memory list
  • 100MB result set transferred for a query that needs 1KB
  • Subtle: calling ToList() inside a helper method breaks composition

Materialise Only When

  • You need to pass the result outside EF's pipeline
  • You're iterating the result multiple times
  • You're mapping to DTOs after applying all server-side filters

Real-World Gotcha

  • Repository pattern hiding ToList() internally breaks upstream filtering
  • Generic repositories returning IEnumerable<T> instead of IQueryable<T>
  • Unit tests pass (small data) — production collapses (full table)
❌ PREMATURE MATERIALISE — full table loaded, then filtered in C#
var allOrders = await _db.Orders.ToListAsync(); // FULL TABLE IN MEMORY
var filtered  = allOrders.Where(o => o.Status == OrderStatus.Pending);
var paged     = filtered.Skip(0).Take(20); // In-memory, no SQL optimisation
✅ COMPOSABLE PIPELINE — all work pushed to SQL engine
// Build IQueryable — no SQL executed yet
IQueryable<Order> query = _db.Orders.AsNoTracking();

// Conditionally compose — still IQueryable
if (filter.Status.HasValue())
    query = query.Where(o => o.Status == filter.Status);

if (filter.CustomerId != null)
    query = query.Where(o => o.CustomerId == filter.CustomerId);

// Project + paginate BEFORE materialise — all in SQL
var result = await query
    .Select(o => new OrderDto { /* ... */ })
    .OrderByDescending(o => o.CreatedAt)
    .Skip(page * size).Take(size)
    .ToListAsync(); // ← Only here does SQL execute
ARCHITECT NOTE › Repository pattern anti-pattern: never return IEnumerable<T> from a repository for entities — always return IQueryable<T> to allow callers to compose. The materialisation belongs at the Application/Service layer, not the data layer. This is a common senior-level design mistake.
07
Keyset Pagination vs Offset Pagination Query Efficiency
SKIP/TAKE degrades logarithmically — Keyset scales O(log n)
Query Cost at Scale Page Reads Sort Cost

Core Concept

Offset (SKIP/TAKE): SQL Server reads and discards the first N rows before returning the page. Page 500 of 20 = discard 10,000 rows. Cost grows with page number. Keyset: uses a WHERE clause on the last seen key value — jumps directly to the correct index position. O(log n) regardless of page depth.

Offset Pagination — Production Problems

  • Page 1000 of infinite scroll = 20,000 row discard on every request
  • Deep paging under load causes query timeout cascades
  • "Ghost rows": concurrent inserts cause duplicates/skips across pages
  • Total count query (COUNT(*)) requires full scan

Which To Use

  • Keyset: infinite scroll, feeds, real-time lists, high-volume APIs
  • Offset: admin UIs with explicit page numbers, reports with known small datasets, when you need total count for UI
  • Cursor = keyset with opaque token (hide implementation from API consumers)

Deployment Impact

  • At 1M rows, page 500 with offset: ~2-5s; keyset: <10ms
  • Offset pages under DDoS: trivial to cause DB CPU exhaustion
  • Keyset requires stable sort column — design your schema accordingly
❌ OFFSET PAGINATION — degrades at scale
// SKIP reads and discards rows — expensive on deep pages
var page = await _db.Orders
    .OrderBy(o => o.Id)
    .Skip(pageNumber * pageSize)  // ← Discards N rows every time
    .Take(pageSize)
    .ToListAsync();
✅ KEYSET PAGINATION — O(log n) constant performance
// First page: no cursor
var firstPage = await _db.Orders
    .AsNoTracking()
    .OrderBy(o => o.Id)
    .Take(pageSize)
    .ToListAsync();

// Subsequent pages: seek past last seen Id
var nextPage = await _db.Orders
    .AsNoTracking()
    .Where(o => o.Id > lastSeenId)  // Index seek — not scan
    .OrderBy(o => o.Id)
    .Take(pageSize)
    .ToListAsync();

// Opaque cursor (hide internal Id from API consumer)
var cursor = Convert.ToBase64String(
    BitConverter.GetBytes(nextPage.Last().Id));
ARCHITECT NOTE › Keyset requires a deterministic stable sort. Use (CreatedAt, Id) composite cursor for time-ordered feeds — CreatedAt can have ties, Id breaks them. Expose as an opaque base64 cursor in your API contract to decouple clients from your internal sort key choice.

Compiled Queries — Eliminate Plan Generation Cost Runtime Perf
Cache the LINQ expression tree compilation for hot paths
CPU — Expression Compilation Delegate Allocation Query Plan Cache

Core Concept

Every EF LINQ query is compiled from an expression tree to SQL on first execution — parsing, visiting, parameterising, and caching the plan. For extremely hot paths (auth checks, per-request lookups, health checks), this compilation cost is measurable. EF.CompileAsyncQuery() pre-compiles and caches as a typed delegate, eliminating recompilation entirely.

Problem If Ignored

  • EF's internal query cache has eviction under memory pressure
  • Cold start latency spikes on first request after deployment
  • High-frequency simple lookups (auth tokens, session checks) accumulate compilation overhead
  • Not critical for 99% of queries — target only verified hot paths

When Compiled Queries Pay Off

  • Authentication/authorisation lookups (every request)
  • Session validation queries
  • Per-entity load in tight loops (import processing)
  • Benchmark first — premature optimisation applies here

Impact

  • Microsecond savings per call — matters at 100K+ RPS
  • Eliminates expression tree GC allocations on hot path
  • Predictable cold-start: all queries pre-compiled at startup
✅ COMPILED QUERY — pre-compiled delegate, zero re-compilation
public static class CompiledQueries
{
    // Compiled once at class initialisation — reused for every call
    public static readonly Func<AppDbContext, Guid, Task<User?>>
        GetUserById = EF.CompileAsyncQuery(
            (AppDbContext db, Guid id) =>
                db.Users.AsNoTracking()
                        .FirstOrDefault(u => u.Id == id));

    public static readonly Func<AppDbContext, string, Task<RefreshToken?>>
        GetActiveToken = EF.CompileAsyncQuery(
            (AppDbContext db, string token) =>
                db.RefreshTokens
                  .AsNoTracking()
                  .FirstOrDefault(t => t.Token == token && !t.IsRevoked));
}

// Usage — zero expression tree work at call site
var user = await CompiledQueries.GetUserById(_db, userId);
ARCHITECT NOTE › EF Core 8+ has improved its internal query cache significantly. Profile with BenchmarkDotNet before committing to compiled queries — the maintenance cost (static coupling, non-composable) is real. Use them where benchmarks prove savings, not by convention.
09
Disable AutoDetectChangesEnabled for Bulk Writes Bulk Writes
Change detection O(n²) cost — disable it for batch import scenarios
O(n²) Detection Cost Snapshot Overhead

Core Concept

EF calls DetectChanges() automatically before SaveChanges(), before most query executions, and when accessing navigation properties. With 10,000 tracked entities, each DetectChanges() call compares all 10K entity snapshots — O(n) per call, O(n²) in a loop. Disabling it during batch operations and calling manually or chunking dramatically reduces cost.

Problem If Ignored

  • Importing 10K rows with tracking: each Add() triggers DetectChanges
  • Processing becomes exponentially slower as tracked set grows
  • Memory for 10K snapshots: ~40-200MB depending on entity size
  • LOH allocation for large entities → Gen2 GC pauses

Pattern: Chunk + Disable + Re-enable

  • Disable before bulk AddRange loop
  • Chunk SaveChanges in batches (500-1000 rows)
  • Clear ChangeTracker between chunks to release memory
  • Always re-enable in finally block

Deployment Impact

  • 10K row import: 45s with defaults → 3s with disabled tracking
  • Chunking prevents transaction log growth per batch
  • ChangeTracker.Clear() prevents memory leak between chunks
❌ DEFAULT — DetectChanges O(n²) on every Add()
foreach (var record in importedRecords)   // 50,000 records
{
    _db.Products.Add(record); // Each Add triggers DetectChanges on ALL tracked!
}
await _db.SaveChangesAsync();
✅ DISABLED + CHUNKED — linear cost, bounded memory
_db.ChangeTracker.AutoDetectChangesEnabled = false;
try
{
    const int chunkSize = 500;
    var chunks = importedRecords.Chunk(chunkSize);

    foreach (var chunk in chunks)
    {
        await _db.Products.AddRangeAsync(chunk); // No DetectChanges per item
        await _db.SaveChangesAsync();
        _db.ChangeTracker.Clear();  // Release snapshot memory between chunks
    }
}
finally
{
    _db.ChangeTracker.AutoDetectChangesEnabled = true;  // Always restore
}
ARCHITECT NOTE › For truly massive imports (>100K rows), bypass EF entirely and use Rule #10 (SqlBulkCopy). This rule targets medium-scale bulk ops (1K–50K) where you still want EF's model validation, interceptors, and value converters to run.
10
SqlBulkCopy — Maximum Insert Throughput Bulk Writes
Bypasses the entire SQL INSERT pipeline — raw bcp-equivalent speed
Minimal Log I/O DataReader Streaming No Row-by-Row Parsing

Core Concept

SqlBulkCopy uses SQL Server's TDS bulk load protocol — the same mechanism as the bcp utility and SSIS. It streams data directly into the table, bypassing INSERT statement parsing, plan compilation, and individual row processing. Minimally logged in simple recovery model — transaction log impact is a fraction of equivalent INSERTs.

Problem If Ignored

  • 100K INSERT statements: minutes; SqlBulkCopy: seconds
  • Each INSERT: parse SQL, compile plan, write to log, commit
  • EF AddRange still emits individual or batched INSERTs — not bulk
  • Transaction log fills during large imports without bulk ops

Use SqlBulkCopy When

  • Importing >50K rows
  • ETL/data migration pipelines
  • IoT/telemetry high-frequency writes to staging tables
  • NOT when: you need EF interceptors, value converters, domain events

Deployment Impact

  • 1M rows: SqlBulkCopy ~10-30s; EF AddRange ~10-30 min
  • Transaction log: minimally logged = smaller backup window
  • Requires table lock by default — schedule during off-peak
✅ SqlBulkCopy — production-grade with DataReader streaming
public async Task BulkInsertOrdersAsync(IEnumerable<Order> orders)
{
    var table = BuildDataTable(orders); // Map entities to DataTable

    using var conn = new SqlConnection(_connectionString);
    await conn.OpenAsync();

    using var bulkCopy = new SqlBulkCopy(conn,
        SqlBulkCopyOptions.TableLock |        // Lock table for duration
        SqlBulkCopyOptions.UseInternalTransaction, null)
    {
        DestinationTableName = "dbo.Orders",
        BatchSize            = 1000,           // Commit every 1000 rows
        BulkCopyTimeout      = 300             // 5 min timeout
    };

    // Explicit column mapping — protects against schema changes
    bulkCopy.ColumnMappings.Add("Id",         "Id");
    bulkCopy.ColumnMappings.Add("CustomerId", "CustomerId");
    bulkCopy.ColumnMappings.Add("TotalAmount","TotalAmount");
    bulkCopy.ColumnMappings.Add("CreatedAt",  "CreatedAt");

    await bulkCopy.WriteToServerAsync(table);
}

// EFCore.BulkExtensions library — wraps SqlBulkCopy with EF model awareness
await _db.BulkInsertAsync(orders, options => {
    options.BatchSize    = 2000;
    options.SetOutputIdentity = true;  // Get back DB-generated IDs
});
ARCHITECT NOTE › Consider EFCore.BulkExtensions (free, open-source) which wraps SqlBulkCopy and respects EF model configuration (value converters, column names, shadow properties). For Postgres, use COPY via Npgsql's BeginBinaryImport. For Azure SQL, test with bulk insert against Hyperscale — behaviour differs from on-prem.

SQL Inspection — ToQueryString() & Logging Observability
Never trust LINQ — always verify the generated SQL
Query Verification Plan Analysis N+1 Detection

Core Concept

ToQueryString() returns the parameterised SQL EF would generate without executing it — use during development and testing. SQL logging via EnableSensitiveDataLogging() + structured logging captures every query at runtime. Together these give you full observability into EF's SQL emission without an external profiler.

Problem If Ignored

  • Client-side evaluation silently moves WHERE to C# (EF3 removed this but subtleties remain)
  • N+1 queries invisible without SQL inspection
  • Cartesian explosion from multiple Includes missed until profiling
  • Parameterisation failures cause SQL injection vectors or plan cache misses

Logging Strategy by Environment

  • Dev: Console + EnableSensitiveDataLogging()
  • Staging: Structured logs (Seq/Elastic) with slow query threshold
  • Prod: Log queries > 500ms only + APM (Application Insights / Datadog)

Deployment Impact

  • Full query logging in prod: significant performance overhead — DON'T
  • EnableSensitiveDataLogging() in prod = data breach risk — NEVER
  • Slow query threshold logging = high signal, low noise
✅ QUERY INSPECTION — development + production safe patterns
// ─── Dev: Inspect without executing ──────────────────
var query = _db.Orders
    .Where(o => o.CustomerId == customerId)
    .Include(o => o.Items);

Console.WriteLine(query.ToQueryString()); // Inspect SQL in dev/tests

// ─── DI Registration: tiered logging ─────────────────
services.AddDbContext<AppDbContext>(options =>
{
    options.UseSqlServer(connectionString)
           .LogTo(
               action:      sql => logger.LogDebug(sql),
               categories:  [DbLoggerCategory.Database.Command.Name],
               minimumLevel: env.IsDevelopment()
                             ? LogLevel.Information
                             : LogLevel.Warning)
           .EnableDetailedErrors(env.IsDevelopment())
           .EnableSensitiveDataLogging(env.IsDevelopment()); // NEVER prod!
});

// ─── Slow query detection (prod-safe) ────────────────
options.AddInterceptors(new SlowQueryInterceptor(thresholdMs: 500));

// SlowQueryInterceptor — logs queries exceeding threshold
public class SlowQueryInterceptor : DbCommandInterceptor
{
    public override DbDataReader ReaderExecuted(DbCommand cmd,
        CommandExecutedEventData evt, DbDataReader result)
    {
        if (evt.Duration.TotalMilliseconds > _thresholdMs)
            _logger.LogWarning("SLOW QUERY {Duration}ms: {Sql}",
                evt.Duration.TotalMilliseconds,
                cmd.CommandText[..Math.Min(500, cmd.CommandText.Length)]);
        return result;
    }
}
ARCHITECT NOTE › Integrate with OpenTelemetry: EF Core emits System.Diagnostics.Activity spans for every query. Configure OTEL to export to Jaeger/Datadog/Application Insights — you get distributed traces from HTTP request → EF query → SQL execution → network → DB response with zero additional instrumentation code.
