SOLID Principles
The Production Reality

Not a university lecture. This is how SOLID actually plays out in large-scale .NET systems — with the violations that rot codebases and the patterns that prevent them.

C# / .NET 8+ ASP.NET Core DI & IoC Architecture 15+ YOE
Section 0
§0 TL;DR — Senior Summary

Principal Engineer Brief

SOLID is a forcing function for maintainability, not a dogma. Robert C. Martin codified these five principles in the early 2000s to describe what he'd observed in well-structured OO codebases. Each principle targets a specific class of coupling — temporal, logical, data, interface, or dependency coupling — that causes systems to become unmaintainable under change. The #1 production risk of SOLID violations isn't runtime failure — it's velocity collapse: the codebase becomes so tightly coupled that every change triggers a ripple of unintended breakage across modules. The #1 tech debt risk is the God Class (SRP violation) — a class that accumulates responsibility over time and eventually becomes the only object anyone can reason about the system through. Use SOLID as a diagnostic vocabulary during architecture review, not as a compliance checklist; knowing why a class violates SRP is more valuable than citing the rule.

How We Got Here — The Evolution

Pre-1990s — Procedural Era

Monolithic Procedures & Global State

COBOL, Fortran, early C: everything in one procedure, data in global structs. Change one subroutine and you had no way to reason about what else would break. Coupling was total. The term "spaghetti code" originates here.

1990s — OOP Adoption (C++, early Java)

Classes Introduced, But Same Problems at Class Scale

OOP introduced encapsulation and inheritance. But developers began writing God Classes — OrderProcessor that handles parsing, validation, persistence, emailing, and reporting. The class boundary replaced the procedure boundary. Coupling remained high, just differently packaged.

2000–2003 — Robert C. Martin Codifies SOLID

The Principles Are Named

Martin synthesised observed patterns from well-maintained OO codebases into five principles. They weren't invented — they were discovered in code that had survived changes gracefully. The acronym "SOLID" was coined by Michael Feathers.

2005–2015 — .NET & C# Mainstream

DI Containers, Interfaces, and Testability

ASP.NET, then Autofac, then Unity made DI practical. SOLID became the foundation for testable .NET code. Interface-per-dependency became the idiom. Teams learned to invert dependencies onto abstractions. Interface explosion (ISP violations in the other direction) appeared as a new problem.

2016–Present — .NET Core & Modular Systems

Microservices Reframe the Principles at Service Level

SOLID now applies at two levels: class/module level (traditional) and service/bounded-context level. SRP maps to bounded context isolation. DIP maps to event-driven contracts. The principles remain valid; the unit of analysis has shifted. AI-generated code frequently violates SRP and ISP — code review must catch this.

Principle 1 of 5
S Single Responsibility Principle
The most violated principle in every .NET codebase. Also the most misunderstood.
S

Single Responsibility Principle

Robert C. Martin, 2003
A class should have only one reason to change.
Note: this is about reasons to change — not about having only one method. A class can have 20 methods and still have one reason to change. A class with two methods that satisfy two different business actors already violates SRP.
💡
Architect's Lens: The word "responsibility" is deceptive. Martin's later clarification is sharper: a class should serve a single actor — a group of stakeholders who have authority to change its requirements. If finance and operations both have authority to change InvoiceProcessor, it violates SRP regardless of how focused the code looks.

The Problem Before SRP

Classic ASP.NET WebForms and early MVC codebases routinely produced controllers like this — God Classes that handled everything from HTTP parsing to database writes to email delivery:

❌ The God Class — Classic .NET Anti-Pattern C# 
// A real class from a 2010-era ASP.NET MVC project — 1,200 lines
public class OrderController : Controller
{
    // Reason 1: HTTP request parsing (HTTP team owns this)
    [HttpPost]
    public ActionResult ProcessOrder(OrderViewModel vm)
    {
        // Reason 2: Validation (business rules team owns this)
        if (vm.Quantity <= 0) return View("Error");
        if (vm.CustomerId == Guid.Empty) return View("Error");

        // Reason 3: Database writes (DBA team owns this)
        var order = new Order { CustomerId = vm.CustomerId, Total = vm.Total };
        _db.Orders.Add(order);
        _db.SaveChanges();

        // Reason 4: Inventory (warehouse team owns this)
        _db.Inventory.Where(i => i.ProductId == vm.ProductId)
                     .First().Stock -= vm.Quantity;
        _db.SaveChanges();

        // Reason 5: Email notification (comms team owns this)
        var smtp = new SmtpClient("mail.company.com");
        smtp.Send("noreply@co.com", vm.Email, "Order Confirmed", "...");

        // Reason 6: PDF receipt (legal team owns this)
        var pdf = new PdfDocument();
        // ... 200 more lines ...
        return View("Confirmation");
    }
}
💥
Why this kills you in production: When finance changes invoice format, you touch the same class that stores orders and sends emails. A merge conflict in OrderController is practically guaranteed every sprint. More dangerously: you cannot unit test order validation without an SMTP server and a database.
✅ SRP Applied — Decomposed by Actor C# 
// Each class has exactly ONE reason to change
// HTTP request handling only — changed by API contract team
[ApiController]
public class OrdersController : ControllerBase
{
    private readonly IOrderService _orders;

    public OrdersController(IOrderService orders) => _orders = orders;

    [HttpPost]
    public async Task<IActionResult> Create(CreateOrderRequest request)
    {
        var result = await _orders.PlaceOrderAsync(request);
        return result.Match(
            success => CreatedAtAction(...),
            error   => BadRequest(error)
        );
    }
}

// Business orchestration only — changed by operations team
public class OrderService : IOrderService
{
    private readonly IOrderRepository    _repo;
    private readonly IInventoryService   _inventory;
    private readonly INotificationService _notifications;
    private readonly IOrderValidator     _validator;

    public async Task<Result<OrderId>> PlaceOrderAsync(CreateOrderRequest req)
    {
        // Each step is owned by a focused class — no direct coupling
        var validation = await _validator.ValidateAsync(req);
        if (!validation.IsValid) return Result.Fail(validation.Errors);

        var order = Order.Create(req);
        await _repo.AddAsync(order);
        await _inventory.ReserveAsync(req.Items);
        await _notifications.OrderPlacedAsync(order);

        return Result.Ok(order.Id);
    }
}

// Validation only — changed by business rules team
public class OrderValidator : IOrderValidator
{
    public async Task<ValidationResult> ValidateAsync(CreateOrderRequest req)
    {
        // Fluent Validation, pure logic, no I/O — trivially unit testable
        if (req.Quantity <= 0) return ValidationResult.Fail("Quantity must be positive");
        if (req.CustomerId == Guid.Empty) return ValidationResult.Fail("Invalid customer");
        return ValidationResult.Ok();
    }
}
⚠️ The Subtle Trap — Over-Decomposition C# 
// Looks like SRP. Every class does "one thing". But this is fragmentation, not separation.
// All three classes below change together every time the order model changes.
// That's one reason to change split across three classes — the opposite of the goal.

public class OrderQuantityValidator  { /* validates only quantity */ }
public class OrderCustomerIdValidator { /* validates only customer id */ }
public class OrderTotalValidator     { /* validates only total */ }

// Problem: "validation of an order" is ONE responsibility.
// The correct decomposition is ONE OrderValidator that handles all order rules.
// Split only when different actors (different stakeholders) own different rules.

Principle 2 of 5
O Open/Closed Principle
The principle that strategy and decorator patterns were invented to satisfy.
O

Open/Closed Principle

Bertrand Meyer, 1988 — reframed by Robert C. Martin
Software entities should be open for extension, but closed for modification.
Meyer's original meaning: a class is closed once it's deployed and depended upon — you don't reopen it. Martin's modern meaning: design with abstractions such that new behaviour can be added by writing new code, not by editing existing code. The implementation technique: strategy pattern, decorator pattern, plugin architectures.
⚠️
The Pre-OCP World: Before OCP thinking, every new discount type, every new payment provider, every new export format required modifying the same class and re-testing the entire system. An if/else chain or switch statement growing by one case per sprint is the canonical OCP violation signature.
❌ OCP Violated — The Expanding Switch Statement C# 
// Every new discount type requires modifying this class.
// This class will be touched by every sprint, forever.
// Cannot be tested without covering all branches.
// A new developer will inevitably miss a case.
public class PricingEngine
{
    public decimal CalculateDiscount(Order order, string discountType)
    {
        return discountType switch
        {
            "seasonal"  => order.Total * 0.10m,
            "loyalty"   => order.Total * 0.15m,
            "bulk"      => order.Quantity > 100 ? order.Total * 0.20m : 0,
            // Sprint 8: added "flash" — modified this class
            "flash"     => DateTime.UtcNow.Hour is >= 12 and <= 14 ? order.Total * 0.25m : 0,
            // Sprint 15: added "referral" — modified again
            "referral"  => order.HasReferralCode ? order.Total * 0.05m : 0,
            _           => 0
        };
    }
}
✅ OCP Applied — Strategy Pattern with DI Registration C# 
// PricingEngine NEVER changes when a new discount type is added.
// New discount = new class implementing IDiscountStrategy.
// Register it in DI and the engine picks it up automatically.

public interface IDiscountStrategy
{
    string DiscountType { get; }
    decimal Calculate(Order order);
    bool IsApplicable(Order order);
}

// Existing class — never touched again after initial creation
public class SeasonalDiscountStrategy : IDiscountStrategy
{
    public string DiscountType => "seasonal";
    public bool IsApplicable(Order order) => true;
    public decimal Calculate(Order order) => order.Total * 0.10m;
}

// New in Sprint 8: zero changes to PricingEngine required
public class FlashSaleDiscountStrategy : IDiscountStrategy
{
    public string DiscountType => "flash";
    public bool IsApplicable(Order order) =>
        DateTime.UtcNow.Hour is >= 12 and <= 14;
    public decimal Calculate(Order order) => order.Total * 0.25m;
}

// PricingEngine is CLOSED for modification, OPEN for extension via DI
public class PricingEngine
{
    // All strategies injected — new one added? DI resolves it automatically
    private readonly IEnumerable<IDiscountStrategy> _strategies;

    public PricingEngine(IEnumerable<IDiscountStrategy> strategies)
        => _strategies = strategies;

    public decimal CalculateDiscount(Order order, string discountType)
    {
        var strategy = _strategies
            .FirstOrDefault(s => s.DiscountType == discountType
                              && s.IsApplicable(order));
        return strategy?.Calculate(order) ?? 0m;
    }
}

// Program.cs — new strategy added by registering, not modifying
builder.Services.AddScoped<IDiscountStrategy, SeasonalDiscountStrategy>();
builder.Services.AddScoped<IDiscountStrategy, FlashSaleDiscountStrategy>();
⚠️ Subtle Trap — OCP via Inheritance (Classic Mistake) C# 
// Looks OCP-compliant. But inheritance-based extension in C# leads to
// fragile base class syndrome. A change to the base class breaks all subtypes.
// Strategy/composition is almost always the right OCP implementation in .NET.

public abstract class ReportGenerator
{
    public virtual string Generate(ReportData data) => BuildBase(data);
    protected abstract string BuildBase(ReportData data);
    // Adding ANY virtual method here is a breaking change for all subclasses
}

// After 8 subclasses and 3 years, you have 47 virtual method overrides
// and no developer can confidently change the base class.
// Prefer: IReportRenderer strategy + decorator pipeline instead.

Principle 3 of 5
L Liskov Substitution Principle
The most technically precise of the five. Violations cause silent bugs, not obvious failures.
L

Liskov Substitution Principle

Barbara Liskov, 1987 — formal type theory foundation
If S is a subtype of T, then objects of type T may be replaced with objects of type S without altering any of the desirable properties of the program.
Practically: a subclass must honour the contract of its base. It must not strengthen preconditions, weaken postconditions, throw exceptions the base never threw, or change invariants. If you need a runtime is check to call a method safely, you have an LSP violation.
⚠️
The Rectangle/Square Problem — The Classic Example: A Square IS-A Rectangle mathematically, but is NOT substitutable for Rectangle in code — setting Width changes Height, which violates the caller's assumption that dimensions are independent. LSP forces you to question inheritance hierarchies that feel natural.
❌ LSP Violated — The Classic Rectangle/Square C# 
public class Rectangle
{
    public virtual int Width  { get; set; }
    public virtual int Height { get; set; }
    public int Area() => Width * Height;
}

public class Square : Rectangle
{
    // LSP violation: setter changes both dimensions — breaks Rectangle's contract
    public override int Width  { set => base.Width = base.Height = value; }
    public override int Height { set => base.Width = base.Height = value; }
}

// This code breaks silently with a Square:
void ResizeWidth(Rectangle r)
{
    r.Height = 4;
    r.Width = 5;
    // Expected: Area = 20. With Square: Area = 25. Silent data corruption.
    Assert(r.Area() == 20); // FAILS for Square
}
✅ LSP Applied — Real-World Payment Provider Example C# 
// Payment processing scenario — a common LSP violation site in enterprise .NET
public interface IPaymentProvider
{
    // CONTRACT: returns PaymentResult — never throws, never returns null
    Task<PaymentResult> ChargeAsync(PaymentRequest request);
    // CONTRACT: amount must be positive, within 90 days of charge
    Task<RefundResult> RefundAsync(RefundRequest request);
}

// Both implementations fully honour the contract:
public class StripePaymentProvider : IPaymentProvider
{
    public async Task<PaymentResult> ChargeAsync(PaymentRequest request)
    {
        // Stripe supports any positive amount — contract honoured
        var charge = await _stripe.ChargeCreateAsync(...);
        return PaymentResult.FromStripe(charge);
    }
    // Supports refunds up to 90 days — contract honoured
    public async Task<RefundResult> RefundAsync(RefundRequest request) { ... }
}

public class PayPalPaymentProvider : IPaymentProvider
{
    public async Task<PaymentResult> ChargeAsync(PaymentRequest request)
    {
        // PayPal also returns PaymentResult — contract honoured
        var resp = await _paypal.ExecutePaymentAsync(...);
        return PaymentResult.FromPayPal(resp);
    }
    public async Task<RefundResult> RefundAsync(RefundRequest request) { ... }
}

// Consumer: works correctly with ANY registered IPaymentProvider
// Zero type-checking. Zero null guards. Zero exceptions from broken contracts.
public class PaymentService
{
    private readonly IPaymentProvider _provider;
    public PaymentService(IPaymentProvider provider) => _provider = provider;

    public async Task ProcessAsync(Order order)
    {
        var result = await _provider.ChargeAsync(new PaymentRequest(order));
        // No: if (provider is StripePaymentProvider) { ... }
        // No: if (result == null) throw ...
        // Just consume the contract-guaranteed result
        if (result.Success) await FulfillOrderAsync(order);
    }
}
⚠️ The Subtle LSP Violation — NotSupportedException C# 
// The most common LSP violation in enterprise .NET:
// An implementation throws NotSupportedException for a method the interface declares.
// This FORCES every consumer to wrap calls in try/catch — or discover it at runtime.

public class ReadOnlyOrderRepository : IOrderRepository
{
    public Task<Order> GetByIdAsync(Guid id) => /* works */;

    // LSP violation: IOrderRepository contract says this should work
    public Task AddAsync(Order order)
        => throw new NotSupportedException("Read-only repository");

    // FIX: Segregate the interface (see ISP section)
    // IReadOnlyOrderRepository { GetByIdAsync }
    // IOrderRepository : IReadOnlyOrderRepository { AddAsync }
    // ReadOnlyOrderRepository implements IReadOnlyOrderRepository only
}
Principle 4 of 5
I Interface Segregation Principle
The principle that directly prevents the NotSupportedException LSP violation above.
I

Interface Segregation Principle

Robert C. Martin — coined while consulting at Xerox
Clients should not be forced to depend on interfaces they do not use.
Large "fat" interfaces force implementing classes to provide stub or throwing implementations for methods they don't support — a direct path to LSP violations. The solution: many small, focused interfaces. In .NET, this pairs naturally with DI composition and the multiple-interface registration pattern.
❌ ISP Violated — The Fat IWorker Interface (Classic) C# 
// Fat interface: forces every implementer to stub what they don't support
public interface IOrderRepository
{
    // Read operations
    Task<Order>       GetByIdAsync(Guid id);
    Task<List<Order>> GetAllAsync(OrderFilter filter);
    // Write operations
    Task            AddAsync(Order order);
    Task            UpdateAsync(Order order);
    Task            DeleteAsync(Guid id);
    // Reporting (completely different actor)
    Task<OrderSummary> GetSummaryAsync(DateRange range);
    Task<byte[]>       ExportToCsvAsync(DateRange range);
}

// Now a read-only cache implementation MUST provide stubs:
// public Task AddAsync(Order order) => throw new NotSupportedException();
// And an OLAP reporting store MUST provide CRUD stubs it never needs.
✅ ISP Applied — Segregated Interfaces with CQRS Alignment C# 
// Separate interfaces by client consumption pattern
public interface IOrderReader
{
    Task<Order>       GetByIdAsync(Guid id);
    Task<List<Order>> GetAllAsync(OrderFilter filter);
}

public interface IOrderWriter
{
    Task AddAsync(Order order);
    Task UpdateAsync(Order order);
    Task DeleteAsync(Guid id);
}

public interface IOrderReporter
{
    Task<OrderSummary> GetSummaryAsync(DateRange range);
    Task<byte[]>       ExportToCsvAsync(DateRange range);
}

// Full SQL implementation: can implement all three
public class SqlOrderRepository : IOrderReader, IOrderWriter, IOrderReporter
{
    // All methods meaningfully implemented — no stubs, no throws
}

// Redis read cache: implements IOrderReader ONLY — no forced stubs
public class RedisOrderCache : IOrderReader
{
    public async Task<Order> GetByIdAsync(Guid id)
    {
        var cached = await _redis.GetAsync($"order:{id}");
        return cached is null ? null : JsonSerializer.Deserialize<Order>(cached);
    }
    public async Task<List<Order>> GetAllAsync(OrderFilter f) => ...;
    // No AddAsync, no UpdateAsync, no ExportToCsvAsync — not its concern
}

// Consumers depend only on what they need
public class OrderQueryHandler(IOrderReader reader)    { ... } // reads only
public class OrderCommandHandler(IOrderWriter writer)   { ... } // writes only
public class OrderReportService(IOrderReporter reporter) { ... } // reports only

// DI registration
builder.Services.AddScoped<IOrderReader,   RedisOrderCache>();    // cache for reads
builder.Services.AddScoped<IOrderWriter,   SqlOrderRepository>(); // SQL for writes
builder.Services.AddScoped<IOrderReporter, SqlOrderRepository>(); // SQL for reports
✅
Architect's take: ISP is where SOLID and CQRS naturally converge. Separating IOrderReader from IOrderWriter is the same decision as separating query models from command models. If you're applying CQRS in your .NET system, you're already doing ISP correctly.
ISP — Interface Segregation vs Fat Interface
Left: fat interface forces Redis cache to implement methods it cannot support. Right: segregated interfaces allow each implementation to declare only what it can deliver.

Principle 5 of 5
D Dependency Inversion Principle
The foundation of testable .NET code and the entire DI ecosystem.
D

Dependency Inversion Principle

Robert C. Martin — precursor to all modern DI containers
(a) High-level modules should not depend on low-level modules. Both should depend on abstractions.
(b) Abstractions should not depend on details. Details should depend on abstractions.
In .NET: your domain and application layers reference interfaces only. Infrastructure (SqlServer, Redis, SMTP) implements those interfaces. The dependency arrow is reversed from the traditional direction — hence "inversion".
💡
DIP ≠ Dependency Injection. DI is a technique to achieve DIP. DIP is the principle. You can violate DIP even with a DI container — by passing concrete types through it instead of interfaces. The container resolves; the principle is about what you wire to what.
❌ DIP Violated — High Level Depends on Low Level C# 
// OrderService is a high-level domain class.
// It directly instantiates SqlOrderRepository — a low-level infrastructure detail.
// To test OrderService: you need a SQL database.
// To switch to Cosmos: you rewrite OrderService.

public class OrderService
{
    // DIP violation: concrete dependency, instantiated directly
    private readonly SqlOrderRepository _repo = new SqlOrderRepository();
    private readonly SmtpEmailSender _email = new SmtpEmailSender("mail.co.com");

    public async Task PlaceOrderAsync(Order order)
    {
        await _repo.AddAsync(order); // coupled to SQL
        await _email.SendAsync(...); // coupled to SMTP
    }
}
✅ DIP Applied — Clean Architecture Dependency Graph C# 
// DOMAIN layer (innermost) — owns the abstractions, depends on nothing external
// Domain/Abstractions/IOrderRepository.cs
namespace Domain.Abstractions;

public interface IOrderRepository
{
    Task<Order> GetByIdAsync(Guid id, CancellationToken ct = default);
    Task        AddAsync(Order order, CancellationToken ct = default);
}

public interface IEmailSender
{
    Task SendAsync(EmailMessage message, CancellationToken ct = default);
}

// APPLICATION layer — depends on Domain abstractions, not on Infrastructure
// Application/Orders/OrderService.cs
public class OrderService
{
    // Constructor injection — both resolved by DI at runtime
    private readonly IOrderRepository _repo;
    private readonly IEmailSender     _email;

    public OrderService(IOrderRepository repo, IEmailSender email)
    {
        _repo  = repo;
        _email = email;
    }

    public async Task PlaceOrderAsync(Order order, CancellationToken ct = default)
    {
        // OrderService has NO knowledge of SQL, SMTP, or any concrete tech
        await _repo.AddAsync(order, ct);
        await _email.SendAsync(new EmailMessage(...), ct);
    }
}

// INFRASTRUCTURE layer — implements Domain abstractions, depends on concrete tech
// Infrastructure/Persistence/SqlOrderRepository.cs
public class SqlOrderRepository : IOrderRepository
{
    private readonly AppDbContext _db;
    public SqlOrderRepository(AppDbContext db) => _db = db;

    public async Task AddAsync(Order order, CancellationToken ct)
    {
        _db.Orders.Add(order);
        await _db.SaveChangesAsync(ct);
    }
    public Task<Order> GetByIdAsync(Guid id, CancellationToken ct)
        => _db.Orders.FindAsync(new object[] { id }, ct).AsTask();
}

// COMPOSITION ROOT (Program.cs) — the ONLY place concretions are named
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddScoped<IEmailSender, SmtpEmailSender>();
builder.Services.AddScoped<OrderService>();
⚠️ DIP Trap — Interface in the Wrong Layer C# 
// DIP trap: the interface is defined in the Infrastructure layer.
// This means Application depends on Infrastructure's namespace — still wrong direction.
// IOrderRepository must live in Domain, not in Infrastructure.Abstractions.

// WRONG namespace:
namespace Infrastructure.Abstractions;  // 🚫 Domain should own its ports
public interface IOrderRepository { ... }

// Application layer would then reference Infrastructure — circular dependency risk
// and violation of the inversion: Infrastructure still "owns" the abstraction.

// CORRECT: Domain owns its own abstractions
namespace Domain.Abstractions;          // ✅
public interface IOrderRepository { ... }

§6 How the Principles Interact
SOLID principles are not independent — they reinforce and enable each other. Understanding their relationships is what separates architect-level thinking from developer-level compliance.
When you apply…It enables…Because…
SRPOCP becomes feasibleSmall, focused classes are easier to make open/closed because there's less to protect from modification
ISPLSP violations eliminatedSmall interfaces mean no implementation is forced to stub unsupported methods — the root LSP violation in practice
DIPOCP implemented correctlyDepending on abstractions is the mechanism by which extension without modification is achieved
LSPDIP contracts honouredIf subtypes violate LSP, swapping one DI registration for another breaks the consumer — undermining the whole point of DIP
OCP + DIPPlugin architectureAbstractions (DIP) + extension without modification (OCP) = new implementations added as plugins, zero existing code changed

Anti-Library
§7 What NEVER to Do
The fastest way to improve is to know what the worst developers do — and never do it.
🚫 NEVER: Put business logic in a Controller or a DbContext
💥 BECAUSE: Controllers have an HTTP lifetime and mix HTTP concerns (model binding, response shaping) with domain logic. DbContext holds EF change tracking — business logic there creates untestable, infrastructure-coupled code that cannot be unit tested without SQL Server.
📍 INSTEAD: Controllers call application services. Application services contain domain orchestration. DbContext stays in the repository layer.
🚫 NEVER: Use 'new ConcreteClass()' inside a class that isn't a factory
💥 BECAUSE: Direct instantiation violates DIP and makes the dependency impossible to replace. Sealing the dependency means you cannot mock it in tests, cannot swap implementations, and cannot intercept it for cross-cutting concerns (logging, retry, caching).
📍 INSTEAD: Declare constructor parameters as interfaces. Let the DI container resolve them at runtime.
🚫 NEVER: Create interfaces with more than 5–7 methods
💥 BECAUSE: Large interfaces force implementers to stub methods they don't support (NotSupportedException), which is a direct LSP violation waiting to happen. Every new method on a published interface is a breaking change for all implementers.
📍 INSTEAD: Segregate by client consumption pattern. IOrderReader and IOrderWriter instead of IOrderRepository with 10 methods.
🚫 NEVER: Use 'is' or 'as' type checks in business logic
💥 BECAUSE: Runtime type checking is the code smell that proves LSP was violated. If you're casting to a subtype to call a method not on the interface, either the interface is wrong or the hierarchy is wrong. Type-checking grows — you'll add more cases as more subtypes appear.
📍 INSTEAD: Put the variant behaviour on the abstraction using polymorphism, or use a visitor/strategy pattern if the type hierarchy is genuinely varied.
🚫 NEVER: Create a "Util", "Helper", or "Manager" class
💥 BECAUSE: These names are SRP violations waiting to happen. "Manager" has no defined responsibility boundary — anything remotely related gets added. Within 6 months, OrderManager is a 1,500-line God Class that every developer is scared to touch.
📍 INSTEAD: Name classes by their responsibility: OrderFulfillmentService, OrderPriceCalculator, OrderStatusTransition. If you can't name it, the class doesn't have a clear reason to exist yet.
🚫 NEVER: Apply all 5 SOLID principles to every class from the start
💥 BECAUSE: SOLID is a response to change pressure. Applying DIP + ISP + OCP upfront to a class that has only one caller and one implementation adds indirection overhead with no benefit. This is premature abstraction — it makes the codebase harder to navigate without reducing any real coupling.
📍 INSTEAD: Apply SOLID when you feel the pain it prevents: when the second implementation appears (DIP), when the third conditional branch appears (OCP), when the first God Class method count crosses 500 lines (SRP). SOLID is a refactoring tool first.
🚫 NEVER: Put the interface in the Infrastructure layer
💥 BECAUSE: The whole point of DIP is that high-level modules own the abstractions they depend on. If Infrastructure.Abstractions.IOrderRepository lives in the infrastructure project, the Application project must reference Infrastructure — undoing the inversion and creating the circular dependency risk that DIP was designed to prevent.
📍 INSTEAD: Domain and Application layers own their abstractions (ports). Infrastructure implements them (adapters). This is the Ports and Adapters / Hexagonal Architecture pattern.
Quick Reference
§8 Code Review Reference Card
Keep this open during architecture review sessions.
SOLID — The 5 Mental Models

The 5 Principles in One Sentence Each

  • S — One class, one actor who can demand a change
  • O — Add behaviour by adding a class, not editing one
  • L — Any subtype must honour the base type's contract fully
  • I — Never force a class to implement what it doesn't use
  • D — Domain calls interfaces; Infrastructure implements them

Code Review Red Flags

  • Class over 200 lines → potential SRP violation
  • Switch on type string → likely OCP violation
  • NotSupportedException in override → LSP violation
  • Interface with 8+ methods → ISP violation
  • new ConcreteClass() in business code → DIP violation

The 3 Questions in Code Review

  • Who owns this class? If two teams can demand changes, SRP is violated.
  • What does it take to add a new X? If the answer is "edit this class", OCP is violated.
  • Can I swap the implementation in DI without touching the consumer? If no, DIP is violated.

Production Readiness

  • Business logic testable without database
  • New behaviour = new file, not edited file
  • No is / as in domain logic
  • Interfaces in Domain, not Infrastructure
  • No class named Manager, Helper, or Util
  • Each class has a clear named responsibility

MediatR (SRP via command/query handlers) · FluentValidation (SRP — validation as a separate concern) · Polly (OCP — new resilience policies without modifying existing ones) · AutoFac / Microsoft.Extensions.DI (DIP — composition root pattern) · Entity Framework Core (Repository pattern enables DIP over raw SQL) · Clean Architecture template (the canonical .NET DIP project structure).
✅
Architect's Final Take: SOLID is not a checklist — it's a vocabulary for identifying coupling. Every violation maps to a coupling type (logical, temporal, data, interface, concretion). Use the principles diagnostically: when a PR is hard to review, identify which SOLID principle it violates and name the coupling category. That vocabulary transforms vague "feels wrong" intuitions into actionable architectural decisions.
